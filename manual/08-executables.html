8. Executables (.xex)

Atari binary-load programs run straight from the SD card, or straight from your PC over the USB-C cable, with no DOS disk involved.

What a .xex file is

A .xex is an Atari "binary load" executable — the format DOS loads with its L command. It starts with the two bytes $FF $FF and contains one or more segments, each with a start and end address, plus optional INITAD (run this before loading the next segment) and RUNAD (jump here when done) entries. Many games and demos are distributed this way.

Running a .xex from the OSD

  1. Copy the .xex to the SD card.
  2. Open the OSD (F12 or S2), select 1) D1: → 1) Attach (.atr/.xfd/.xex)....
  3. Pick the .xex in the browser (it is listed alongside .atr and .xfd files).

The Atari cold-boots straight into the program and the menu closes by itself. The main menu's D1: line shows the .xex name while it is attached.

A .xex boots from D1: only. The D2: browser lists .xex files too, but they are not disk images, so attaching one there fails with a Mount failed message.

What happens behind the scenes

  • The firmware serves a small built-in 6502 loader as a virtual boot disk on D1:, with the .xex bytes following it sector by sector. Any disk that was in D1: is taken out.
  • The Atari is cold-booted with the OPTION key held by the firmware, so BASIC is disabled and the whole RAM is free for the program.
  • The loader handles the full multi-segment format: the $FFFF header, several segments, and the INITAD / RUNAD vectors.

The file is checked before booting: one without the $FF $FF header is refused with Not a valid .XEX (missing $FFFF header).

Running a .xex from the PC

With the PC Link set up (see PC Link), atari.py run sends the file over the USB-C cable and boots it in one go — about five seconds from your assembler to the running program:

python3 tools/atari.py run mygame.xex

The file lands on the SD card (in the /PC folder by default) and boots exactly as an OSD attach would; the D1: line shows it too. Related commands: atari.py eject pops the virtual disk off D1:, and atari.py reset ejects and cold-boots (with --warm for a warm start and --keep to keep the .xex attached).

Ejecting

The .xex stays attached to D1: after it has loaded, so a reset would boot it again. Remove it from either side:

  • OSD: 1) D1: → 3) Detach — or simply attach an .atr to D1:, which takes the drive back.
  • PC: python3 tools/atari.py eject.

Detaching from the OSD does not reboot the machine; the running program continues until you reset.

Limitations

  • Page $0600–$07FF. The loader lives in this area while the program is being loaded. A program that itself loads into $0600–$07FF can clash with the running loader and fail to start. Relocating the loader to high RAM is a possible future fix.
  • Some demanding titles show intermittent graphics glitches — see Known issues. In particular a few PAL-timed games misbehave on this NTSC-only machine, whether loaded as .xex or otherwise.
  • Only D1: can boot a .xex; it is not a DOS "L" load into a running system, but a cold boot.
