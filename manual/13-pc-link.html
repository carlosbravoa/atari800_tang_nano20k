13. PC Link

The USB-C cable that powers and flashes the board also carries a serial link to the Atari: send files, boot programs, type, read the screen and capture the printer from your PC.

13.1 What it is

The board's onboard BL616 chip bridges a USB serial port to the Atari firmware. No extra hardware is needed: the same USB-C cable that powers and flashes the board is the link. Two programs in the repository's tools/ folder use it, and both share one protocol library (atari_link.py):

  • tools/atari.py — the command-line tool.
  • tools/atari_gui.py — the same things in a desktop window (Linux/Windows).

The Atari has its own power and keeps running whatever the PC does, so a failed command is always safe to retry. Transfers run at about 11 KB/s and the machine keeps running during them (mounted disks stay live). Firmware memory access is Atari-first by design; measured impact on machine timing is zero even under continuous peek load. Flashing the board is unaffected by the link.

13.2 One-time setup

Linux

pip install pyserial
sudo apt install python3-tk     # desktop app only
sudo modprobe ftdi_sio          # if no /dev/ttyUSB* appears
# make the module load permanent:
echo ftdi_sio | sudo tee /etc/modules-load.d/ftdi_sio.conf

Windows

Install pyserial the same way (pip install pyserial). The FTDI VCP driver arrives via Windows Update automatically. Python builds from python.org already include Tk, so the desktop app needs nothing extra.

Which port?

The board enumerates as a pair of serial ports. The second port of the pair is the bridge, and the tools auto-pick it. If autodetection ever guesses wrong, pass -p with the port name (for example -p /dev/ttyUSB1 or -p COM5); every command accepts -p PORT. Then check the link:

python3 tools/atari.py ping        # -> "A8OK — bridge is alive (both directions)"
python3 tools/atari.py ports       # list candidate ports
Before flashingClose log, kbd and the desktop app before using the Gowin programmer. They hold the serial port.

13.3 The command-line tool: atari.py

Run every command as python3 tools/atari.py <command> from the repository folder. All commands take -p PORT.

13.4 The desktop app: atari_gui.py

python3 tools/atari_gui.py
  • Connect (top) — port auto-detected; shows A8OK when the Atari answers.
  • Left column — Send file…, Run .xex… (with a Destination folder field, default PC, with a progress bar), Eject, Warm start, Cold boot, Ping. Text files (.txt/.lst/.bas) sent here are auto-converted to ATASCII line endings. A remotely-run .xex appears on the OSD's D1: line and can be detached from either side.
  • Log tab — live firmware output; Clear / Save….
  • Type tab — write or load a BASIC listing, then Type it on the Atari (line by line, self-healing across USB hiccups).
  • Printer tab — everything the Atari prints collects here (§13.6): Save as .txt, Save as PDF, Print…, Clear.
  • Live Keys tab — click the box and type straight onto the Atari (Backspace/Esc/Tab/Enter included). Press F12 on the real keyboard to take the machine back; the app detaches cleanly.

13.5 Typing rules

  • Typing reaches the machine only while the OSD menu is closed (an open menu eats keystrokes, the same masking rule as the physical keyboard).
  • Characters map to the Atari keyboard layout.
  • Speed is about 18 characters per second. After every RETURN the firmware settles for 250 ms, because BASIC tokenises the line while its keyboard buffer holds only one character; multi-line listings arrive intact.
  • Long type sessions can occasionally drop the USB link. The tools self-heal and retry; for big programs prefer the H: + ENTER route in §13.11.

13.6 Printer capture

The firmware emulates the P: printer (SIO device $40, 820-style). Anything the Atari prints — LPRINT from BASIC, PRINT #n to P:, LIST "P:", AtariWriter's print function — arrives on the PC as text. It works on a stock machine with no drivers, because the P: handler lives in the OS ROM.

  • With the CLI, printed text shows up as PRN: lines in atari.py log.
  • In the desktop app it collects in the Printer tab: Save as .txt, Print… to your system printer, or Save as PDF for a period-correct 5×7 dot-matrix rendering (word-processor margins stripped, width auto-fitted to the document).

13.7 The D4: hard drive (HDD.ATR)

A disk image named exactly HDD.ATR in the root of the SD card is auto-mounted on D4: at every power-on, with no OSD interaction. It is the natural target for files you exchange with the PC: copy an image to the card with python3 tools/atari.py send mydos_big.atr HDD.ATR, then power-cycle, because the automount runs once at firmware start. status shows the mount and the log says boot: hdd mounted on D4. Formats, DOS pairing (MyDOS recommended) and the fail-safe rules are covered in chapter 6, Disks.

13.8 The H: shared folder

H: is a CIO device (a peer of P:, E: and K:), not a disk, so DOS does not list it and does not need to. Files written to H: land as plain files in /HDD on the SD card's FAT filesystem — the same folder the PC writes into with send … HDD/NAME. It is the bridge for text and data files between the two worlds.

Install it first, from the PC:

python3 tools/atari.py hdd-install
# -> "H: installed at $0900-$0CB2 (above MEMLO), MEMLO raised to $0D00."

The installer reads MEMLO and places the handler just above it (with a resident DOS booted it simply lands higher), then raises MEMLO past its end. The handler lives in Atari RAM and is session-scoped: RESET clears it, so re-run hdd-install to restore it.

Type NEW in BASIC right after installingBASIC only re-reads the raised MEMLO on NEW; until then its program area still overlaps the handler. Install first, NEW, then ENTER or type your program.

Use it from BASIC:

REM --- write ---
OPEN #1,8,0,"H:NOTES.TXT"
PRINT #1;"WRITTEN FROM BASIC"
CLOSE #1

REM --- read back ---
OPEN #1,4,0,"H:NOTES.TXT"
DIM A$(40):INPUT #1,A$:PRINT A$
CLOSE #1

REM --- store/recall a program (plain ATASCII, PC-readable) ---
LIST "H:PROG.LST"
ENTER "H:PROG.LST"

REM --- directory with sizes ---
OPEN #1,6,0,"H:"
DIM D$(40)
FOR I=1 TO 999:INPUT #1,D$:PRINT D$:NEXT I
CLOSE #1

REM --- delete ---
XIO 33,#1,0,0,"H:NOTES.TXT"

OPEN modes: 4 = read, 8 = write, 9 = append, 6 = directory, 12 = update.

13.9 Network (N:) and modem (R:)

N: network device — prototype

An N: SIO device, relayed to a network processor running on the PC, exists as a working prototype in the source tree: a real FujiNet weather application has fetched and rendered live data on the bench. It is not yet release-grade under sustained load and is planned for a later release.

TODO: N: usage instructions for end users (to be confirmed when the feature ships)

R: 850 modem for BobTerm — work in progress, opt-in, default OFF

BobTerm (and other 850-modem terminal programs) can dial a live telnet BBS through the USB-C cable. The firmware answers the OS cold-start handler poll and serves the real Altirra 850 handler (FujiNet-compatible); tools/atari_net.py --modem is the PC-side modem (Hayes AT commands, telnet).

  1. Enable it: OSD → Options → Modem (R:) → ON (persisted by Save changes as modem=1). When OFF (the default) the feature has zero effect on normal use: the firmware stays silent to the OS poll, so a gaming boot is unchanged.
  2. Obtain the two Altirra binaries. They are Avery Lee's Altirra work, redistributed by the FujiNet project, and are deliberately not included in this repository. Download them from the FujiNet firmware repository at 
    fujinet-firmware/data/webui/device_specific/BUILD_ATARI/850handler.bin
fujinet-firmware/data/webui/device_specific/BUILD_ATARI/850relocator.bin
    and drop them into tools/fujinet_850/. Expected sizes: handler 1281 bytes, relocator 341 bytes. Check their upstream licence before redistributing them.
  3. Stage them on the SD card — the firmware streams them from /PC/850HAND.BIN and /PC/850REL.BIN during the cold-start handler bootstrap (only when the Modem option is ON): 
    python3 tools/atari.py send tools/fujinet_850/850handler.bin   PC/850HAND.BIN
python3 tools/atari.py send tools/fujinet_850/850relocator.bin PC/850REL.BIN
  4. Alternatively, python3 tools/atari.py r-install installs the R: handler into a running session above MEMLO (type NEW in BASIC afterwards; RESET clears it, re-run to restore). Then start atari_net.py --modem on the PC and run BobTerm.
StatusWork in progress: some text garbles under fast BBS bursts. Usable for BBS sessions, not yet release-grade under sustained load.

13.10 Telemetry and remote debugging

The bridge answers everywhere, even at the ROM-failure screen, so a machine that will not boot can be examined and rescued from the PC.

  • status returns one line starting with ST. Fields: u: firmware uptime in ms; bs: boot stage (0 start, 1 SD ok, 2 options, 3 ROMs tried, 4 running); rom: ROM-load result; x: a virtual .xex is active; m: four digits, one per drive D1:–D4: (1 = mounted); c:/s:/st: last SIO command, sector and status; e: SIO error count; cn: the firmware stack canary; plus hd: and nt: counters for the H: handler and the network device.
  • screen dumps the 40×24 text screen — "remote eyes" on the READY prompt or your program's output.
  • peek/poke inspect and modify Atari RAM live (checksummed). Watch the jiffy clock at 0x12 tick to prove the 6502 is alive; poke 0x2C8 for a pink border.
  • log shows boot-stage markers: boot: sd ok → boot: roms 0 → boot: running (and boot: hdd mounted on D4 when HDD.ATR is present).
  • ROM-failure rescue: if the machine stops at the ROM-failure screen, send the missing ROM files over the cable and press a key on the Atari to retry.
  • Reading the answers: a status reply names the stage the firmware is stuck at. Total serial silence means the machine never reached the firmware at all — power-cycle it.

13.11 Recipes

Paste a short BASIC program

Close the OSD, then:

python3 tools/atari.py type mygame.bas
# or from a pipe:
cat mygame.bas | python3 tools/atari.py type -

On the Atari: RUN (and SAVE "D4:MYGAME.BAS" if a DOS is booted).

Load a long program without the typing

Push the listing as a file and ENTER it (needs H: installed, so a BASIC session):

python3 tools/atari.py send --text mygame.lst HDD/MYGAME.LST
ENTER "H:MYGAME.LST"
RUN

Push-and-run a compiled program

python3 tools/atari.py run build/demo.xex     # sends + cold-boots into it

The program shows up on the OSD's D1: line; atari.py eject removes it.

Get a listing from the Atari to the PC

There is no file download over the bridge yet, but the Atari can print to the PC:

LIST "P:"

It arrives as text in atari.py log or in the desktop app's Printer tab (then Save as .txt).

Share data files both ways

  • PC → Atari: python3 tools/atari.py send --text data.txt HDD/DATA.TXT, then OPEN #1,4,0,"H:DATA.TXT" on the Atari.
  • Atari → PC: write to H: from BASIC (OPEN #1,8,0,"H:OUT.TXT" …). The file is now /HDD/OUT.TXT on the SD card; the PC reads it directly the next time it can read the card. (A bridge get command is planned.)

Remote debugging

python3 tools/atari.py status                 # boot stage, mounts, SIO health
python3 tools/atari.py screen                 # what's on the Atari screen now
python3 tools/atari.py peek 0x12 3            # jiffy clock (is it alive?)
python3 tools/atari.py poke 0x2C8 0x35        # tint the border pink

13.12 Limitations

Use the tools that came with your firmware versionSince v3.2.1 the bridge only accepts framed commands (a sync byte, the command, and a check byte), so stray bytes on the USB link can no longer trigger a reset or a memory write. The tools/ folder of the same release always matches; an older atari.py against a newer firmware simply gets no answer.
  • H: is session-scoped: RESET clears it; re-run hdd-install. It installs above MEMLO and coexists with a resident DOS, but BASIC only picks up the raised MEMLO on NEW.
  • No file download from the SD card over the bridge yet. Atari → PC text goes via the printer path (LIST "P:" / LPRINT); a get command is planned.
  • The HDD.ATR automount runs once at firmware start. After you send a new one, power-cycle the board.
  • type needs the OSD closed.
  • Long type sessions can occasionally drop the USB link; the tools self-heal and retry, but the H: + ENTER route avoids it for big programs.
  • Known issue: F12 can be unresponsive while a PC serial session is engaged; the S2 button still opens the OSD (see chapter 15).

13.13 If the bridge stops answering

RecoveryIf the bridge chip stops answering after a USB storm (for example a very long typing session), unplug the board's USB cable, wait ten seconds, and plug it back in. The Atari side is unaffected.
